# Problem Reports Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let any signed-in user report a standalone problem from the phone (text, severity, up to 5 photos/videos, GPS when available, a site), offline-capable; let managers in scope see reports on the phone and the web, create a task from one, or close one with a comment; notify managers on creation and the reporter on close/resolve.

**Architecture:** A new `problem_reports` entity with its own tables, NestJS module (`apps/api/src/problem-reports/`), contracts file, api-client group, mobile offline store + outbox commands + sync section, a "Problemlər" tab with three screens, and a second tab on the web Problems page. Checklist problems (`execution_problems`) are untouched. Every pattern copies the SP5 tasks module: client-generated ids, presigned PUT media, data-scope SQL, outbox commands with device-time conversion, `mergePull`.

**Tech Stack:** NestJS 11 + Drizzle 0.45 + Postgres (RLS), zod 4 contracts, Expo SDK 57 / RN 0.86 (expo-sqlite+SQLCipher, expo-camera, expo-image-picker, **new: expo-location**), React 19 web with TanStack Router/Query + shadcn, Vitest / Jest + Testing Library.

**Spec:** `docs/superpowers/specs/2026-11-06-mobile-home-and-problem-reports-design.md`, §3–§12 (Part 1, §7.1–7.2, is already merged on this branch as `2026-11-06-mobile-home-refresh.md`).

## Global Constraints

- Every i18n key exists in az, en and ru (`Shape<Translations>` typecheck + `i18n.test.ts`); new notification types need `notifications.types.*` and `notifications.templates.*` entries.
- Limits come from contracts: text 1–2,000, close comment 1–1,000, media ≤ `MEDIA_LIMITS.problemMaxMedia` (5), sync window 30 days, known ids ≤ 100.
- Data scope rules fail closed on an unknown scope (`default: never` switch), like `TaskScope.covers`.
- Reports are never deleted or edited by the reporter; the API has no PATCH/DELETE for them.
- Migrations: `0018_problem_reports.sql` generated by `pnpm --filter @edildy/api db:generate` from the schema, then `0019_problem_reports_security.sql` hand-written and appended to `drizzle/meta/_journal.json` (copy the 0010 pattern: `idx`, `version: "7"`, `when`, `tag`, `breakpoints: true`).
- Mobile SQLite: migration v5 is **appended** to `MIGRATIONS`; shipped entries are never edited.
- Every endpoint runs inside the tenant transaction (`this.db.tx()`), audit entries via `AuditService.record`, events via `DomainEvents.emit`.
- Tests: API integration tests under `apps/api/test/` with `createTestApp` (Testcontainers Postgres); mobile under Jest with `createTestServices`; run `pnpm --filter @edildy/<pkg> test|typecheck|lint` before each commit of that package.

## Review Focus

1. **A manager in the `site_subtree` scope must not see a report at a site outside their subtree**, even when the reporter is their subordinate by `manager_id` (Task 6 scope matrix pins all four scopes with and without `assignments.view`).
2. **A report sent twice (retry after a lost connection) must not duplicate**: same id → same row, and a different reporter reusing the id gets 409 (Task 6 idempotency test).
3. **A report created offline with media must survive an app restart before sync**: the SQLite rows and the outbox commands are written in one transaction; media files persist in the documents directory (Task 10 store test "create writes row, media and two commands atomically").
4. **A report whose site the reporter no longer belongs to when the phone syncs** is refused with `SITE_NOT_ALLOWED` and shown as "Göndərilmədi: …", never silently dropped (Task 11 sync-engine test).
5. **Location permission denied, or a fix that never arrives**, must still let the worker send after the 15 s window, with `location: null` and a confirmation (Task 14 screen test).
